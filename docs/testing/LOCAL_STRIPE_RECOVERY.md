## Final behavior

- Ledger RPC faults, empty/malformed/tokenless claims and completion faults fail closed. Every acquired claim has a fresh UUID token. Success/failure compares the token, so a superseded worker cannot overwrite the recovered worker's result. Active duplicates return 503; completed duplicates return 200.
- Subscription create/update/delete now use one fenced transaction for the subscription row and pro linkage. Creation can be reclaimed after a worker dies; an invoice waiting for that row can then complete. Creation replay preserves an existing row and repairs a legacy partial pro linkage. Deletion creates a terminal tombstone, older events cannot replace a newer pro subscription, and updates refresh the Stripe snapshot after a durable per-subscription reservation. Application checks the reservation token under a row lock, so a blocked earlier fetch cannot commit after a newer reservation/application, including equal-second events. Ownership across subscription IDs uses Stripe's immutable subscription `created` timestamp; event clocks order only the same subscription ID. Invoice and subscription transactions share the pro-then-subscription lock order.
- Owned paid invoices arriving before the local subscription now fail and remain retryable. Foreign invoices retain existing skip behavior.
- Invoice payment insertion, monthly counters, payment date and dunning reset now use one transactional RPC. A unique paid-invoice identity covers distinct Stripe event IDs and null payment intents. The transaction locks and validates the current ledger claim, then subscription/pro rows. Duplicate invoices perform no second counter reset. Failure after insertion rolls back the insertion and effects together. A crash after commit but before outer completion can safely replay.
- Lead payment insertion and capture now use one fenced transactional RPC. It validates acceptance/session/quote/pro/amount and current status, rejects voided/refunded or mismatched captures, and validates an existing payment rather than swallowing an arbitrary unique violation. Repeated successful delivery neither inserts another payment nor rewrites captured timestamps. Checkout creation retains PR 154's stable idempotency option.
- Lead handoff is now enqueued uniquely in the existing protected `notification_logs` table inside fulfillment. The route awaits one send attempt; failure leaves a durable job with backoff, and a crashed dispatch can be reclaimed with a fresh token. `retryPendingPaidLeadHandoffs` provides a bounded queue drain. No real email was sent and no scheduler or endpoint was installed. Admin-sale alerting retains its existing behavior.
- PR 154 supplied the initial fail-closed checks, validation and retry approach. Its unfenced lease migration is superseded locally with token-aware RPCs and transactional fulfillment. No competing remote PR was created.
- PR 159's exact server helper and missing-Stripe guards were integrated into the overlapping webhook/unlock routes. Guards run before DB work, and preserve the claim logic, validated metadata and checkout idempotency. The other PR 159 routes/UI changes are outside this patch; integration should retain them from that PR.
- Existing `createServiceRoleClient` remains unchanged. Its missing-credential guard is covered by an offline regression. No products, prices, keys, checkout modes, auth policies or grants changed.

## Remaining boundaries and exact design decisions

**Unconverted handlers:** paid invoices, payment-mode lead Checkout Sessions and all three subscription handlers can now safely reclaim processing leases because their DB effects are fenced. Failed-invoice/dunning and dispute handlers still perform separate requests and notifications; their stale processing leases are deliberately not reclaimed. Fencing the final ledger status alone cannot prevent stale business writes. Fully recovering those event types requires their own transactional conversion or an outbox. This remains an explicit release boundary; subscription creation is no longer in this category.

**Retry scheduling:** durable handoff enqueue, individual attempts, lease recovery and a bounded drain are implemented locally. A release owner must wire the drain to an authenticated server-side scheduler using existing service-role access. There is no scheduler in this repository and adding credentials/auth or configuring a live schedule is outside this task. Until wired, failed jobs persist but cannot autonomously wake after the original webhook process exits. This is an operational blocker, not a guarantee of completed mail delivery.

**External mail:** delivery is at least once. A crash after the provider accepts email but before outbox completion can resend it after recovery. The available dependency copy lacks the Resend package, so a provider idempotency API cannot be validated locally without an install, which was prohibited for this continuation. No provider-idempotency call was guessed. Test senders are mocks. Exactly-once external mail needs a verified provider contract and is not claimed. Admin-sale notifications remain fire-and-forget.

**No live success claim:** local checks establish behavior against mocks. They do not establish that production migration permissions, keys, routes, payment methods or webhooks are configured correctly. Previously acknowledged missing-subscription invoices remain unrecovered pending an authorized reconciliation plan.

## Safe reconciliation plan (no query or data change executed)

First inspect only event IDs/statuses and subscription/pro IDs, not full payloads or contact data. Suggested read-only queries are in `LOCAL_STRIPE_RECONCILIATION.sql`. They identify duplicate invoice payment identities, legacy stuck creation events and subscriptions whose pro linkage is missing or points elsewhere.

An unprocessed, owned, stuck subscription-created event is eligible for a normal retry after the new token-aware schema/app is installed and old workers drained. Its transaction either writes both rows, preserves a newer/canceled row, or repairs missing legacy linkage. An already-processed partial creation cannot be repaired by ordinary webhook replay because its ledger correctly deduplicates it. An authorized operator must inspect the current Stripe snapshot, existing subscription and pro state, then target only that proven incomplete event for reconciliation using a fresh claim; never reset all ledger rows or counters. Historical invoice payments require the same evidence before effects are repaired, and duplicate payment rows must be reconciled before the new unique index is installed. No destructive cleanup SQL or blanket replay is supplied.

## Review corrections (local only)

The prior cross-ID `stripe_subscription_event_created` clock is removed from the unapplied proposal. A subscription's event time no longer determines whether it owns a pro relative to a different subscription. An older subscription updated at event time 200 cannot veto a replacement subscription created at 100 when their immutable creation generations are 50 and 100. Later updates to the old subscription also cannot restore its ownership.

`begin_stripe_subscription_sync` durably reserves a UUID generation before retrieval. `sync_stripe_subscription` locks and checks that reservation before any subscription/pro write. If an old retrieval returns after a new reservation/application, it throws `Subscription snapshot superseded`; the route retries with a new reservation and a fresh retrieval instead of reusing the stale snapshot. The deterministic equal-second regression blocks the old retrieval, applies the fresh retrieval, then releases the stale result and verifies it cannot write. The blocked-fetch TypeScript regression uses a contract fake, and a complementary real PostgreSQL test verifies conditional snapshot application and row locking. Full staging/PostgREST verification remains required.

Cancellation guard correction: the pro retains `stripe_subscription_owner_id` alongside immutable `stripe_subscription_created`; only the active linkage is cleared. Equal-generation comparison uses the retained ID (falling back to an existing active ID for legacy rows), so canceled A cannot be replaced or cleared by different B created in the same second. A missing retained identity with a known equal generation also fails closed. This column is part of the unapplied proposal and must be backfilled as a pair with the generation during authorized reconciliation.
